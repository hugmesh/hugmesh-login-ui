# Translation catalogs

`messages.xlf` is the **source template**, produced by `npm run i18n:extract`. It
is generated — never hand-edit it. Everything else here is `messages.<locale>.xlf`,
one per translatable locale.

English is the **source language**. Its text lives in the templates and the
`$localize` calls themselves, so there is no `messages.en.xlf` and there never
will be. That is why the default build (`web_locales=()`) ships **zero** files
from this directory and makes **zero** catalog requests — the smallest artifact
and no network surface at all, which is what a LAN-only or air-gapped mesh needs.

## What ships

Which catalogs end up in the image is the Studio's `web_locales` field
(`--web-locales de,fr`), forwarded to the Dockerfile as `SNAP_WEB_LOCALES`. A
catalog in this directory is *available*, not *shipped*.

| `web_locales` | in the image |
|---|---|
| `()` (default) | *(no `i18n/` directory at all)* |
| `("de",)` | `/usr/share/nginx/html/i18n/de.json` |

## Adding a real locale

1. `npm run i18n:extract` — refresh `messages.xlf` from the source.
2. Copy it to `messages.<locale>.xlf` and add a `<target>` to **every** `<unit>`.
3. `npm run i18n:check` — this fails until the catalog is complete.
4. Add the locale to `web_locales` in the Studio.

**A catalog committed here must be complete.** `npm run i18n:check` enforces it,
and that is deliberate: at runtime a missing message falls back to its English
source *per message*, with only a `console.warn`. That is mixed-language output —
a half-translated login page — and it would ship silently. The gate is what makes
that structurally impossible rather than merely unlikely. If a translation is
in progress, keep the locale out of `web_locales`; don't commit a partial catalog.

## `messages.en-XA.xlf` is not a translation

`en-XA` is a **pseudo-locale**, generated by `npm run i18n:pseudo` and regenerated
after every extract. Every target is the English source with its letters accented
and padded ~30% (`⟦Sîgn în tö…⟧`). It is mechanical, not linguistic — this repo
does not invent translations nobody can vouch for.

It earns its place three ways:

- it is complete by construction, so it proves the whole pipeline (xlf → json →
  `loadTranslations` → `$localize`) and the `web_locales` knob end to end;
- **any text that renders unaccented under `?lang=en-XA` is a string somebody
  forgot to mark up** — it makes half-localization visible instead of subtle;
- the padding surfaces layout that breaks on longer languages before a
  translator is ever paid.

## Editing copy

Changing English text? Edit the template or the `$localize` call, then re-run
`i18n:extract` **and** `i18n:pseudo`. `i18n:check` (gate 4) fails if you forget:
a stale `messages.xlf` means every catalog is "complete" against the wrong set and
your new string renders English in every locale.

Note the ids are explicit (`@@login.heading`) rather than content-hashed, so
rewording English does **not** silently orphan a translation — the id survives and
the reworded source shows up as a diff for translators to review.

The design, and why translation is loaded at runtime rather than at build time,
is documented in [`../app/i18n/locale.ts`](../app/i18n/locale.ts).
